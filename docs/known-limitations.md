# Known limitations

ADAPT 0.1.1 is an **alpha** release, published as a GitHub pre-release. This repository's development tree contains unreleased changes that the 0.1.1 download does not have (failure guidance and `adapt explain`, explicit devices for the MCP tools that act on the phone, the MCP transport label read from the serial, doctor and setup fixes, DeX state parsing and display-flag detection, hardware addresses withheld from `dex pc-probe` output, SSH reason codes, and the native receiver's status file, audio option and `adapt dex receiver-*` commands); where a limit differs between the two, this page says which applies. This page lists what is unproven, experimental, deliberately out of scope or easy to misread. When another document sounds more confident than this one, trust this one, and trust the `claim_boundary` or `note` field of a report where it has one (not every report does).

## How to read the evidence

- **Automated tests are offline.** They mock `adb`, `ssh`, `tailscale`, archives and fixtures, and involve no device. At the 0.1.1 release commit the Python suite has 917 tests in 33 modules. They were run on Windows with Python 3.13. The development tree has more tests; [validation](validation.md) gives the collection count and says that no full-suite result is recorded for it. The release workflow is configured to run them on Ubuntu with Python 3.11 and to install and smoke-test the built wheel on Windows and Ubuntu with Python 3.11 and 3.13 in 0.1.1, and also 3.12 in the development tree (`adapt --help`, `adapt android versions`, `adapt mcp --help`). The checks that are and are not recorded are listed in [validation](validation.md) and [`publication-checks.json`](publication-checks.json). Test counts are not a pass rate, are never added to physical observations, and do not certify distributions, other operating systems or any device.
- **Physical observations cover Samsung devices only, from a Windows 11 host:** a phone with Android 13 (API 33) and a phone with Android 17 (API 37) on pre-release builds, with no date, ADAPT version or commit recorded for any single observation; and, on 2026-11-14, short smoke passes of the released 0.1.1 code on an Android 13 phone (USB), an Android 17 phone and an Android 16 tablet (both wireless debugging), plus native receiver sessions with all three, all from one Windows 11 PC with one Wi-Fi adapter (see [validation](validation.md)). That is a handful of data points, not a compatibility list. Every smoke pass used 0.1.1; the development tree's Python code was run on devices only for the DeX inspection commands during DeX sessions on the Android 17 phone and the Android 16 tablet and for the `adapt dex receiver-*` commands. No device run from Linux is recorded. The offline matrix spans Android 10-17 (API 29-37, including 12L, 9 baselines); every other API level, every other OEM, wearables and TV are untested.
- **Research topologies, generated illustrations and the showcase are not test evidence.** The showcase contains no Android screenshots; its generated panels are source-derived illustrations.
- **No device or host certification.** 0.1.1 is distributed as a wheel and a source archive on GitHub Releases, with `SHA256SUMS.txt` and GitHub build attestations ([releasing](releasing.md)). A checksum shows that a file matches the published list and an attestation ties it to the build workflow; neither certifies any device, host or Android version. The release process publishes nothing to PyPI. No fresh-host run of `adapt setup` or of the README's `pipx` commands against the published URL is recorded.

## Platform and install

| Limitation | Detail |
|---|---|
| Install | Users: Python 3.11+ and `pipx install` of the 0.1.1 wheel from GitHub Releases (use `"adapt-adb[mcp] @ <wheel URL>"` for the MCP server). Contributors: a checkout with `pip install -e .` (add `.[mcp]`). The release workflow installs the built wheel from a local path or file URI; the README's commands against the published URL have not been run from a clean pipx home |
| Python versions | The 0.1.1 workflow installs the wheel with 3.11 and 3.13 only. In the development tree the install job also lists 3.12, but no run of it is recorded, so 3.12 is untested. The suite itself runs in the workflow on 3.11 only, and no job tests the declared dependency minimums (`typer>=0.9.0`, `mcp>=1.0.0`) |
| Host operating systems | Windows 11 and Linux are the targets, but the only recorded device runs are from a Windows 11 host. Linux is offline-tested only (the release workflow runs on Ubuntu), and no device run on Linux is recorded. 0.1.1 treats every Linux host as Debian (`apt`, `plugdev` advice). In the development tree doctor reports Debian-family hosts (from `/etc/os-release`) as `debian` and other Linux as `linux` with distribution-neutral advice; distributions outside the Debian family are untested. macOS is not supported: in the development tree doctor reports it as unsupported and `setup` refuses to run. **Native Debian runtime acceptance is outstanding**, as is fresh provisioning across architectures |
| Platform-Tools | Official Google archive, `adb >= 34.0.0`. In 0.1.1 a distribution-packaged `adb` is treated as outdated; in the development tree one at or above 34.0.0 is a warning and usable, and one below it fails. `setup` fetches the Windows or Linux archive. Google's Linux archive contains x86-64 programs only, so `setup` on Linux needs an x86-64 host; `everything` limits batch setup to x86-64 hosts |
| `setup` prompt | Asks for confirmation when standard input and standard error are both terminals. Without `--yes` and outside a terminal, `setup` stops before downloading or changing anything and reports `aborted_needs_yes`; a non-interactive run does not proceed. Preview with `--dry-run`. In 0.1.1 an aborted setup keeps the doctor pre-check's exit code, so it can exit 0 (for example `setup --force` on a healthy host); in the development tree an aborted or failed setup exits non-zero |
| udev rules | In 0.1.1, `doctor`'s udev action reads `packaging/linux/51-android.rules` from a **source checkout**; the 0.1.1 wheel does not ship it, so a `pipx` install reports the file as not found. In the development tree the wheel includes the file and doctor's advice names its installed path. ADAPT's rules use the `plugdev` group; other distributions may use a different group or ship their own rules package |
| Drivers | ADAPT never installs USB drivers or OS packages; Windows Device Manager and Linux udev changes are manual |
| `doctor --fix` | Prints advice. The interactive menu's `udev` and `setup` choices run privileged or installing steps only when selected |
| Uninstall | `pipx uninstall adapt-adb` removes only the Python package. It leaves in place the Platform-Tools that `setup` installed, the PATH entry `setup` added, a managed scrcpy, snapshot files and any udev rules; ADAPT has no command that undoes them |

## Transports and Tailscale

- **Pairing is not a connection.** Android 11+ needs separate, changing pairing and connection ports; Android 10 needs the legacy USB-first `adb tcpip` flow, which ADAPT never enables for you.
- **A direct Tailscale end-to-end run is unproven.** `adapt tailscale connect|check --mode tls` requires `service.adb.tls.port` to equal the connect port and API >= 30. On the tested Samsung firmware that property was **empty**, so the strict verifier cannot pass there: an open verifier gap, not a confirmed Tailscale failure. `--mode legacy` is a deliberate, separate choice for an already-enabled TCP listener.
- A **private routed VPN/hotspot path did return authenticated ADB commands** and a retained connection recheck in pre-release testing. That is a routed path to one phone, not Tailscale validation.
- A peer being `online`, a TCP port being open (`probe`) or a pairing success proves none of "ADB is authorized and ready". Ports change after reboot or toggling Wireless debugging.
- Android normally allows one active VPN; ADAPT never changes VPN, ACL, subnet-route or exit-node settings. Relay paths can add latency that hurts mirroring. MagicDNS naming and ADB's mDNS discovery are separate; mDNS is not assumed to cross the overlay.
- Direct-peer mode accepts only tailnet node IPs. A **subnet router** reaches a LAN; an **exit node** carries internet-bound traffic only. Neither is selected or configured by ADAPT.
- `ssh` and `tailscale worker-*`: no live SSH acceptance was run. SSH connectivity alone gives no USB, authorized ADB transport or graphical session. There are no hypervisor adapters and no VM or USB-assignment management.

## Detection, tools and builds

- **Root and ROM indicators are not proof.** Missing `su` does not prove a device is unrooted; `test-keys`, root or an unlocked bootloader do not prove a custom ROM; absence of a ROM property does not prove stock. Properties are self-reported, not attested. Bootloader unlock *capability* is separate from lock *state*.
- **Samsung Download/Odin mode is not fastboot.** `detect` does not recognize it.
- **No automatic unlock, flash, root escalation or ROM build.** `tools plan` for `aosp-build`/`lineage-build` explains prerequisites and host suitability only. The tool catalog is manual ROM-tool gathering guidance: **only 2 of 16 catalog tools have automated acquisition** (`platform-tools` via `setup`, `scrcpy` via `tools install scrcpy`). A PATH hit is a location, not provenance or compatibility.
- `everything` also runs a read-only fastboot listing, is not atomic, and in JSON or non-interactive use requires `--yes`.

## Developer profiles, debug and Rapid ADAPT

- **Stay-awake needs USB power.** It ORs only the USB bit into `stay_on_while_plugged_in`, preserving other bits, refuses unknown values, and does not unlock the phone or override device policy. A readback is not proof the screen stays on.
- **Restore is best-effort.** It restores only settings that still hold the profile's value; conflicts abort and are reported, never overwritten. `desktop-testing` may need a manual reboot and some OEMs ignore it. Snapshots can describe your device; protect them.
- **One apply and restore cycle that changed a value is recorded.** On 2026-11-14, with 0.1.1 on an Android 13 phone, `apply --profile touches` read `show_touches` back as `1` (it was `0`) and `restore` read it back as `0`. The same cycle on an Android 17 phone and an Android 16 tablet changed nothing, because the value was already `1`, so there it shows only that the commands ran. Other profiles, rollback, conflicts and partial-failure recovery are offline-tested only.
- `dev-options apply|restore` have no `--json` flag.
- **Debug inspect/plan never attach a debugger.** Persisted settings may differ from a transient runtime selection. `am set-debug-app` (planned, never run by ADAPT) force-stops the target app. A non-debuggable app does **not** prove R8 or a release signer; `app validate` checks only what you request.
- **Rapid ADAPT is integrated planning, not an auto-runner.** It prints commands, executes none, creates no files, and does not supervise or roll back a session. Applied profiles must be restored by you.
- `logs` and MCP log tools: logs and screenshots can hold secrets or personal data and are not redacted. An empty log is not a pass or proof of no crash. Samsung verbose-logging switches are manual vendor controls ADAPT cannot toggle.

## Samsung DeX, displays and the PC bridge

- `dex` experimental activation is limited to Samsung API 33-37 and refuses to replace an existing wireless, DeX or non-internal display. That range is the researched boundary, not a tested one: the only recorded activation attempt was on the API 33 phone.
- **ADAPT's own DeX activation has never been observed succeeding.** On the tested API 33 phone, loopback activation was denied by a firmware permission and a simulated overlay display did not start genuine DeX. The only real DeX sessions in the record were started from the phone with the separate native receiver. Capability presence is not permission, and a secondary or virtual display is not DeX.
- **DeX state detection recognises few firmware forms.** With 0.1.1, `dex inspect` reads only `dumpsys desktopmode`. It reported `unknown` on an Android 13 phone during an active wireless DeX session, because that phone prints its state in a form the 0.1.1 parser does not recognise. The development tree recognises that form for active dual-mode and idle DeX (tested offline against that phone's output; not re-run on the phone). One UI 8 (Android 16 tablet) and One UI 9 (Android 17 phone) have no `desktopmode` service at all, so with 0.1.1 `dex inspect` can only report `unknown` there, and `dex plan-dual-mirror` and `dex mirror` cannot confirm a DeX display. The development tree, only when that service is absent on a Samsung device, confirms DeX from display flags (`FLAG_WIRELESS_DEX_DISPLAY` together with `FLAG_EXTERNAL_DEX_HOSTING` on exactly one external display). That was observed on 2026-11-14 during one wireless DeX session on each of those two devices; on the phone `dex plan-dual-mirror` then produced a plan for the flagged display, but nothing was launched, so scrcpy capturing it is not observed. Standalone and wired DeX were not observed on any device, and other firmware may still report `unknown`. In the development tree, a device that answers no query is reported as unreachable instead of non-Samsung.
- `dex pc-probe` refused with "unrecognized state" on the Android 17 phone during an active wireless DeX session, with 0.1.1 and with the development tree. With 0.1.1 its output includes each display's unique ID, which on the Android 13 phone contained the Wi-Fi display's hardware (MAC) address; the development tree replaces MAC-style addresses in the report with `<hardware-address>` (offline-tested only).
- Display IDs are runtime values and change across connections; never assume the desktop is display 2. `pc-attach` accepts only layouts it recognizes as an active DeX session.
- `dex mirror` needs scrcpy 2.0+; `desktop start` needs 3.1+. Process start is reported, not video or input health.
- **MCP input tools (`tap`, `swipe`, `key`, `type`) target the default display** and have no display targeting; they cannot drive a DeX or virtual display.
- The experimental helper runs as the Android shell user via `app_process`; it is not an APK, root or a Samsung binary, and cleanup after a crash is best-effort.
- A virtual display (`desktop`) tests multi-window behavior only; decorations, focus and input vary by OEM.

## Native Windows receiver

Source lives in `native/windows-receiver`, derived from upstream MIT **DeXDesk** at commit `5070ccda5c363f5ed0b46d1fe7cf2c15c47fc125`, with its license and dependency notices preserved. See its [README](../native/windows-receiver/README.md).

- **Manual build, experimental, not in the Python wheel.** ADAPT never builds, bundles or downloads it. In 0.1.1 no ADAPT command launches it; in the development tree `adapt dex receiver-start --exe PATH --yes`, `receiver-status` and `receiver-stop --yes` start a copy you built, read its status file and ask it to stop.
- **Admission is open by default.** The receiver admits any phone that asks to connect. `ADAPT_DEX_EXPECTED_NAME` (exact Wi-Fi Direct friendly name) and `ADAPT_DEX_EXPECTED_ID` (exact Windows peer ID) are optional restrictions: when set, a phone must match each one that is set. Neither is authentication, because names can be chosen by anyone. TCP 7236 is bound on every IPv4 interface while it runs.
- **It relies on an undocumented Windows advertisement provider** (functions resolved at runtime from `wlanapi.dll`). Windows updates may remove or change it; some Windows versions or radios will not work.
- **Audio is experimental and off by default** in the development tree (`ADAPT_DEX_AUDIO=1` or the `--audio` option of `receiver-start`); 0.1.1 plays no audio. It is not synchronised to video. In three recorded sessions (one per device) the Windows audio output opened at 48 kHz stereo, with underruns. Sound was heard only on the Android 17 phone: its owner reported hearing the phone's sound from the PC and judged the quality great, one listener on one session of about 48 minutes, whose log recorded 9 underruns. Nobody listened with the Android 13 phone or the Android 16 tablet.
- **Failure reason codes are not observed.** The development tree's `status.json` carries reason codes for failures; they come from reading the code and have not been triggered on a radio or a phone.
- **Offline tests.** The source has 20 `#[test]` functions at 0.1.1; a run of all 20 with `cargo test --locked --offline` is recorded in [`publication-checks.json`](publication-checks.json) (2026-11-13, after the open-admission change; the commit is not recorded). The development tree's source has 119; [validation](validation.md) says what is and is not recorded about running them. No CI job runs them, and they do not start the receiver, exercise Wi-Fi Direct or involve a phone.
- **Hardware observations are short and few.** All are from one Windows 11 PC: an earlier revision with an Android 13 phone (a group, decoded frames, one controlled reconnect, and one session held for about a day and a half by an earlier build); the 0.1.1 source for about four minutes with an Android 13 phone; and the development-tree source for about a minute and a half with an Android 13 phone, about 48 minutes with an Android 17 phone (One UI 9) and a short session with an Android 16 tablet (One UI 8), all with admission restricted by device name. Real mouse and keyboard input was confirmed by the owner on the Android 17 phone only; with the Android 13 phone scripted clicks reached the phone as touches but a click on a desktop icon did not open the app, and why is not known; nobody used a real mouse with the tablet. Not established: reconnects on the current source, sessions longer than about 48 minutes, open admission with a device connecting, a release build, and other Android/One UI builds, radios, Windows versions and Debian. It targets x64 Windows. Port 7236 must be free; only one instance runs.
- **The 0.1.1 receiver leaves a stale status file.** After a stop through `stop.request` it still reads `Connected` and `running: true`. In the development tree the final status reads `running: false`, but `phase_code` still reads `connected`.

## MCP

- **No external AI client has been live-accepted**, and MCP-over-SSH has not been exercised. The only recorded MCP sessions are 0.1.1 `--read-only --device` sessions on 2026-11-14 against an Android 13 phone, an Android 17 phone and an Android 16 tablet, driven by a scripted client (the MCP Python SDK for the Android 13 session; not stated for the others): `list_devices`, `device_info` and `screenshot` returned results and `tap` was refused. No tool that acts on the phone has been run against a device, and the unreleased MCP changes (the explicit-device rule, the transport label, the `failure` object and the new error codes) have offline tests only. Configuration snippets are the documented stdio shape, not verified registrations.
- stdio only: no HTTP/SSE, no authentication layer, no remote exposure. Clients limited to remote HTTPS connectors cannot use it.
- `--read-only` removes the 14 mutating tools but not observation of screens and logs; `--device` pins the session to the listed transports and removes `doctor`. In the development tree the 14 tools that act on the phone (`tap`, `swipe`, `key`, `type`, `install_apk`, `app_launch`, `app_stop`, `app_open_link`, `test_run`, `dev_options_apply`, `dev_options_restore`, `permission_grant`, `permission_revoke`, `ui_tap_text`) never choose a device: a call without `device` fails with `need_device`, unless the session was started with exactly one `--device`. Without `--device`, the read-only `device_info`, `screenshot`, `ui_summary` and `logcat_tail` use the only ready device when none is named (and fail when several are ready). In 0.1.1 the five mutating tools also use the only ready device. Pin the session with `--device SERIAL`; `examples/README.md` explains how.
- With 0.1.1, `list_devices` labels a wireless-debugging transport `usb` when the device line carries no transport hint (seen on two devices). In the development tree the label is read from the serial: `tcp` for a host:port endpoint or a wireless-debugging service name, `local` for an emulator, otherwise `usb`. That is a reading of the serial's form, not an observation of the cable; the development-tree behaviour is offline-tested only.
- The 13 build-test loop tools (`app_launch`, `app_stop`, `app_state`, `app_open_link`, `log_mark`, `test_run`, `test_status`, `dev_options_apply`, `dev_options_restore`, `permission_grant`, `permission_revoke`, `ui_tap_text`, `ui_wait`) are offline-tested against faked adb output only; none has been run against a device. Known gaps: `app_state` reports `last_exit` only on Android 11+ (API 30), because `dumpsys activity exit-info` does not exist earlier, and a recorded exit can predate your launch; `pidof` needs Android 7+ and does not count `package:suffix` processes. `app_launch` and `ui_tap_text` act on the default display and the current screen; an app that blocks accessibility dumps (a secure window) cannot be found by `ui_tap_text` or `ui_wait`, and UI dumps can fail while an instrumentation run holds the UI automation service. `log_mark` uses the device clock at millisecond precision where `date` supports `%N`, otherwise whole seconds. `permission_grant` and `permission_revoke` act on the user `pm` defaults to, accept only the Android runtime permissions ADAPT lists (plus the app's own and `android.permission.health.*`), and do not read the new state back. `test_run` needs an installed test APK and an exact runner class; class names with `$` (inner classes) are refused; test runs and their results live in server memory only and are gone when the server exits. `dev_options_apply` snapshots live in a per-user ADAPT state folder; snapshots made with the CLI `--snapshot PATH` are not seen by `dev_options_restore`, and on a device whose identity (serial, build fingerprint, Android user) changes after an update a pending snapshot is no longer found for the new build.
- `ui_summary` may create then remove a temporary file on device storage. `install_apk` reads a host path as your user. In the development tree the server serves static `adapt://` resources and a `help` tool; MCP prompts are not implemented.
- **`adapt agent install` is offline-tested only.** The tests redirect every path to a temporary folder; no client registration it writes (or prints) has been checked against the real client, and the client facts come from each client's documentation read on 2026-11-16. Clients whose facts are third-party or unstated (Windsurf, Zed, Continue, Goose, JetBrains, Junie, Grok) are print-only. Where a client's own command cannot set a tool timeout (Codex, Pi), `install` edits the file instead; the 180 s timeout is the research default, not a measured need. ADAPT never starts or restarts a client, so a registration takes effect when you reload it. A removal through `adapt agent uninstall` covers only entries ADAPT wrote to a file.

## `adapt adb`

A guarded runner, not a shell. Interactive `shell`, streaming `logcat`, `kill-server`, `sudo`, `uninstall` and `pm clear` are refused with no override, and shell programs ADAPT cannot inspect (pipes, redirection, chaining, substitutions, shell indirection) are rejected. Use plain `adb` for deliberate destructive work. Everything else runs as typed, with no snapshot or confirmation: the guard does not stop `adb root`, `adb reboot bootloader`, `adb sideload` or other destructive shell commands. With exactly one ready device and no `-s`, the runner pins that device (the MCP tools that act on the phone do not); with several it asks for `-s`.

## Out of scope

iOS; emulator provisioning or acceleration checks; hypervisor and VM lifecycle management; ROM building, unlocking and flashing; automatic driver installation; HTTP MCP transport; any publishing or repository write performed by ADAPT itself; and certification of any device, OEM or Android version.

## Privacy reminder

Command output, snapshots, logs, screenshots, `dex pc-probe` display IDs and Tailscale peer lists can contain device identifiers, hardware addresses, network names, addresses and personal data. The native receiver's log contains the phone's name, peer ID and addresses only if you set `ADAPT_DEX_LOG_PEER_DETAILS` (development tree; the 0.1.1 receiver always logs them). Review them before sharing, and use placeholders (such as `SERIAL`, `PHONE_PEER` and RFC 5737 addresses like `192.0.2.10`) in public reports.
